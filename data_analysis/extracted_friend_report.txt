1 What the lab asked for
The goal of this lab was to build a small web API that recommends places near a user. A request
gives:
•the user’s current position (lat,long),
•a category such ascafeorbank(cat),
•a search radius (rad),
•a text file describing which roads exist between points on the map (link).
The API must answer with the IDs of the 10 closest locations of that category. Two different
distances are involved, and keeping them apart was the most important part of the whole task:
•the radiusis a plain circle around the user, so it uses the straight-line distance;
•closestmeans the distance you actually travel along the roads.
Some roads between neighbouring points are missing, like in a real city. A place that looks close
on the map can therefore be a long way round by road, and ranking by straight-line distance gives
wrong answers.
I assumed every grid road existed and ranked by Manhattan distance. Then thelink field was
added, and later the TAs shared a samplelink.txt along with its exact format. This report
describes the final version. The API still falls back to the old Manhattan behaviour if a request
comes without a link file.
2 Looking at the data first
Before writing any search code I spent some time checking what the two input files actually look
like. The right algorithm depends heavily on the shape of the data.
2.1 locations.csv
•10,000 rows with the columnsID, Latitude, Longitude, Category.
• The points form an exact100×100grid on the unit square. Every coordinate is k/99
rounded to six decimals (k= 0, . . . ,99), so neighbouring points are1/99≈0.010101apart.
• IDs go row by row:ID = 100 ·row+ col + 1, whererowis the latitude index andcol
the longitude index. Location 1 is at(0 ,0), location 100 at(0 ,1)and location 101 at
(0.010101,0).
• There are 8 categories (bank, cafe, hospital, park, pharmacy, restaurant, school, store) with
exactly 1,250 locations each, scattered randomly over the grid.

Two things followed from this check:
1. Every road joins two neighbours, soevery road has the same length, one grid step.
Road distance is simply a count of steps.
2. The whole network is connected, so every location can be reached, although some only
through long detours.
3 Defining the distances
3.1 Inside the radius
A location is a valid answer only if
√︂
(lati−lat)2 + (long i−long)2 ≤rad.
The radius is in the same units as the coordinates. I allow a tiny tolerance of10−9so that a point
lying exactly on the circle is not thrown out because of floating-point rounding.
3.2 Road distance
I treat the map as a graph: every location is a node and every line of the link file is an edge. The
road distance to a place is thenumber of steps on the shortest routeto it. The API reports
it both asroad_stepsand asgrid_distance=steps×1/99.
I chose to count steps instead of adding up coordinate differences on purpose. In the files, the gap
between two neighbours comes out as either 0.010101 or 0.010102, only becausek/99was rounded
to six decimals. The real spacing is the same everywhere. Adding up the rounded gaps would
make some routes of equal length look a millionth of a unit longer, and floating-point error would
then decide their order. Counting steps uses whole numbers, so two equally long routes really do
compare as equal.

3.3 Where the trip starts
The user joins the road network at thenearest location(straight line). If (lat, long) is a grid
point, which is the normal case, that is just the location at that point. The radius is still measured
from the user’s exact position.
3.4 Ties
Many locations end up the same number of steps away. When that happens, thesmaller ID
wins. This is what a plain stable sort over the CSV order would give, and it makes every answer
deterministic.
I also checked how much this choice matters. Over 600 random queries, other reasonable rules
changed the set of 10 in about 43% of queries, almost always by one ID at the 10th place. Examples
of such rules are using the straight-line distance as the tie-breaker, or taking places in whatever
order a BFS happens to discover them. No rule can match every possible reference implementation,
so I picked the one that is simplest to state and reproduce.

4 The algorithm
4.1 First, the straight forward version
I first wrote the most obvious version, mostly so I would have something to check the faster one
against:
1. read the link file and build the road graph;
4

2. scan all 10,000 locations to find the one nearest the user;
3. run a breadth-first search (BFS) from there over the whole map;
4. scan all 10,000 locations again, keep the ones of the right category inside the radius, sort
them by steps and return the first 10.
It gives correct answers, but it repeats all of this work on every query. It takes about66 ms per
queryon the lab machine, and most of that time is wasted. The road graph is the same for every
query that sends the same file, and we only need the 10 closest places, which are all near the user.
We never need to look at the far side of the map.
4.2 The improved version
I kept the same steps but made each one do only the work it really needs. BFS on a grid is
standard, and splitting a map into squares so you don’t have to check every point is a common
trick.
1. Build the road graph only once per link file.The graph is an adjacency list: a dictionary
from location ID to the list of its neighbours. To turn the coordinates in the file into IDs, I use
another dictionary from the rounded(lat,long)pair to the location, so every line is just two
lookups. The finished graph is cached, keyed by a SHA-1 hash of the file’s contents. When the
same file arrives with the next query, nothing has to be parsed again.
2. Find the start point with a dictionary lookup.The same coordinate dictionary gives
the location under the user in one step. Only if the user is somewhere between grid points do I
fall back to searching nearby cells (step 3) for the nearest location.
3. Find the candidates with a bucket grid.At startup the unit square is cut into17×17
equal cells (side1/17≈0.059), which puts about 4 locations of each category in each cell. Each
category gets its own dictionary from cell to the locations in it. To collect the places inside the
radius, I start at the user’s cell and walk outwards ring by ring (Figure 2). Anything in ringr is
more than( r−1)cell widths away from the user, so once(r−1)×cell size is larger than the
radius, no later ring can contain a valid place and the walk stops. This way only cells near the
user are ever looked at.

Places outside the circle are still walked through, because a road can leave the circle and come

4.3 Why the answer is still correct
• BFS visits all places at stepd before any place at stepd + 1. When it stops after leveld
with 10 or more answers, every unvisited place is at leastd + 1steps away, so it cannot beat
or tie any answer already found.
•Within one level the answers are sorted by ID, which is exactly the tie rule.
•The bucket grid only skips cells whose nearest possible point is already outside the circle.
I did not rely on this reasoning alone. The tests compare the fast version with the straightforward
one on hundreds of random queries (Section 7).

4.4 How much work each version does
Let N be the number of locations,E the number of roads, andV′the number of places closer
than the 10th answer.
Step Straightforward version Improved version
Build the road graphO(E)on every queryO(E)once per link file
Find the start pointO(N)O(1)
Find the candidatesO(N)only the cells near the circle
Road searchO(N+E), the whole mapO(V ′+E′), only up to the 10th answer
Table 2: Work per query.
In practice V′is tiny. Over 2,000 random queries onlink.txt, the BFS reached 90 locations on
average and never more than 209, out of 10,000.
I think this is close to the best that is possible here. To be sure about the 10 nearest places,
any correct method has to look at every location closer than the 10th answer, since a missing or
present road anywhere in that area could change the result, and the early-stopping BFS looks at
exactly that area. Precomputing all distances in advance is not an option: the road file arrives
with the query and can be different each time, and a full table would need10,000×10,000 = 100
million entries. Dijkstra’s algorithm is not needed either, because every road has the same length,
and plain BFS is faster.

Bad input gets an HTTP 400 reply with a shorterror message. That covers a missing field, a
value that is not a number, a negative radius, an unknown category, and a link file that cannot be
read or has no usable lines. If fewer than 10 valid places can be reached, the API returns the ones
it found and adds anote.
5.3 Code structure
The code is written in Python 3 using Flask, and is split into three files:
•proximity.py loads the CSV and holds the bucket grid (candidates, nearest location and
the no-link Manhattan search);
•roads.pyreads the link file into the road graph and runs the BFS;
•app.py handles the HTTP side: reading the fields, accepting the link file in its different
forms, caching, and building the response.

9 Assumptions and limitations
• Link lines are read asLongitude_A Latitude_A Longitude_B Latitude_B , as the TAs
specified. Roads work in both directions and each one is one grid step long.
• The trip starts at the location nearest the user, but the radius is measured from the user’s
exact position.
•A place that cannot be reached by road is not a valid answer.
• Ties are broken by the smaller ID. If the reference answers used a different tie rule, a query
with a tie at the 10th place could differ by one ID.
•radis in coordinate units (the1×1grid), not in kilometres.
• A very large link file should be uploaded or sent by URL rather than pasted into a GET
URL.
